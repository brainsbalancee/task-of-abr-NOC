     3→Project: Customer support helpdesk with two surfaces (customer + staff).

     6→## Architecture overview
     7→
     8→- **Stack**: Next.js 16 (App Router) + TypeScript + Prisma/SQLite + shadcn/ui
     9→- **Two surfaces**:
    10→  - Customer surface (unauthed, open to public): ticket submit, ticket status lookup, AI chatbot
    11→  - Staff surface (authed): ticket queue, ticket detail, reply, AI-suggested draft
    12→- **AI features** (z-ai-web-dev-sdk, backend only):
    13→  - Customer chatbot for self-service (LLM)
    14→  - Staff AI draft-suggestion (LLM)
    15→- **Real-time**: polling (no WebSocket — kept minimal for time box)
    16→- **Security**: input sanitization, rate limiting, signed session tokens for ticket lookup, staff auth

   284→- Known limitations:
   285→  - The rate-limit key is `ip:reply:${ip}` — a separate bucket from lookup (`ip:lookup:`) and from submit (`ip:submit:`), so a customer doing lookup + reply + chat gets 3 independent budgets. This matches the task spec but means a determined attacker gets 20 reply attempts/min AND 20 lookup attempts/min from the same IP. The lookup-side 404-on-wrong-token still closes the enumeration vector for the lookup contract; the reply side inherits the same posture.
